#模块一：System Prompt 工程

它解决什么物理问题

LLM 每一轮对话都会收到完整的 system prompt + 历史消息。System prompt 中的内容是模型行为的"宪法"——它决定模型在无人监督时的默认行为。但 system prompt 的每一个 char 都要在每个 turn 重新计费（即使有 cache，首次创建也需要 cache write 开销）。

物理约束：system prompt 越长 → 每 turn 固定税越高 → 长 session 累积成本呈二次方增长。

行业框架

层级内容加载时机大小控制
L0：不可变核心语言、安全、身份、禁止行为每个 session< 500 tokens
L1：角色规则你的数据分析师角色特有的约束（DB 连接方式、SQL 引擎、表查找规则）每个 session< 2K tokens
L2：项目规则某个 repo/项目独有的规则（如 CBRG_Work/AGENTS.md）进入该项目时< 4K tokens
L3：任务上下文当前任务需要的背景信息按需 tool call 拉取不固定

.cursorrules（Cursor）就是 L1 + L2 层。Anthropic 官方建议 system prompt 控制在 <4K tokens。Vercel v0 按项目类型动态切换 L2 规则。

关键原则：只有"不读就会犯错"的规则放在 always-on 层（L0+L1），其他全部按需拉取（L3）。判断标准：这条规则如果模型不在 context 里看到，它在这类任务中犯错的概率有多高？如果概率低于 10%，就不应该 always-on。

下一步

  • 目标：AGENTS.md always-on 部分 < 4K tokens，专项部分通过 kb-search 或直接 read 按需加载。

#模块二：Skill / Tool 架构

它解决什么物理问题

LLM 的"幻觉"和"偷懒"是两种不同的失败模式：

  • 幻觉：模型不知道正确答案，编一个出来。
  • 偷懒：模型知道应该按步骤来，但直接跳步输出"看起来合理"的结果。

Skill 系统的本质是用 deterministic 的程序逻辑替代 probabilistic 的模型推理——把已知的正确流程固化下来，不给模型"自由发挥"的空间。

行业框架

组件作用设计原则
Trigger 规则关键词/场景 → 激活对应 skill触发词要穷举常见的用户表达方式。
Skill 文件步骤级执行规程每一步都要写 input / output / 验证条件。
禁止清单列出模型在这个任务中不能做的事基于历史犯错记录持续补充。
Tool 权限限制 skill 可用的工具集最小权限原则——审查 agent 不给 exec。

OpenAI 的 Assistants API 和 Anthropic 的 tool use 都遵循这个模式。LangChain 社区的 "structured output + tool binding" 也是同一思路。

关键原则：一个 skill 应该能被一个完全没有上下文的新 session 正确执行——如果你的 skill 依赖"之前的对话中提到过 X"，那它的设计就有问题。

你目前的位置

你的 skill 体系（dashboard-refresh、vendor-vi-dedup、knowledge-sync 等）在设计上是正确的。特别是 vendor-vi-dedup 的 Phase 0→3 分阶和 sql-auditor 的 8 维度检查清单。

下一步

  • 给每个 skill 补充 expected output / exit criteria——目前你的 skill 大多描述了"做什么"，但没有描述"做完之后怎么验证做对了"。
  • 把 data-sanity-checker 从 ad-hoc 调用变成 pipeline 集成——在 run_*.sh 中自动触发。

#模块三：Session 生命周期管理

它解决什么物理问题

LLM 的 context window 是有限资源。每一轮对话，模型要重新读取完整的历史消息。第 N 轮的 prompt token 数 ≈ system_prompt + Σ(前 N-1 轮的消息)。这是一个 O(N²) 的累积过程——你的数据验证了 tokens ≈ 907 × steps²。

同时，Transformer 的注意力机制在超长 context 中会出现 attention dilution——中间位置的信息被模型关注的权重降低（"Lost in the Middle" 现象，Liu et al. 2023）。这意味着你在第 10 步给的关键指令，到第 300 步时模型可能已经"记住但不重视"。

行业框架

策略做法谁在用
Hard step limitSession 超过 N 步自动提示拆分Stripe (80 步), Devin 内部有 soft limit。
Context handoffSession 结束时生成结构化摘要，新 session 读取摘要继续Anthropic 推荐, Cursor "notepad" 功能。
Periodic re-anchoring每 50 步重新注入关键约束Google DeepMind Gemini。
Context compression自动对旧消息做摘要压缩ChatGPT memory, Claude Projects。

关键原则：session 是一次性资源，用完就扔。不要试图在一个 session 里完成所有事情。开新 session 的成本（重新描述上下文 ~500 tokens）远小于维持长 session 的成本（二次方增长 + 注意力衰减）。

你目前的位置

你没有任何 session 管理策略。30 天内有 5 个 session 超过 300 步，最长的达到 709 步。

下一步

  • 在 CLAUDE.md 中加一条简单规则：当 session 超过 80 步时，主动建议用户开新 session 并提供 context handoff 摘要。
  • 更重要的是养成习惯：当你感觉对话变慢、模型开始重复之前说过的话、或者任务方向发生了显著转变时，就是该开新 session 的信号。

#模块四：Evaluation / 质量闸门

它解决什么物理问题

LLM 的输出是 probabilistic 的——同样的 prompt 可能产生不同的输出。你不能假设模型"这次做对了，以后也会做对"。Evaluation 体系的作用是把不确定性的检测从人类转移到自动化系统。

行业框架

层级流程触发条件闸门行为
代码层
sql-auditor		输入 → SQL 审查 → 执行新建/修改 SQL阻断 commit
数据层
sanity-check		数据检查数据产出后，发布前CRITICAL → ABORT
展示层
validate.py		渲染 → 显示检查HTML 产出后，发布前error → ABORT

Airbnb 数据平台团队的做法是在 data pipeline 的每一步都插入 "expectation"（Great Expectations 框架），包括：schema test、volume test、freshness test、custom business logic test。

关键原则：evaluation 必须是 pipeline 中的必经节点，不是可选步骤。如果一个检查需要人记得手动调用，它迟早会被跳过。

你目前的位置

你的 validate.py（7 个）和 sanity_check.py 已经集成到 run_*.sh 的 pipeline 中，这一点做得很好。但 sql-auditor 和 data-sanity-checker subagent 是 ad-hoc 设计，没有自动化触发。

下一步

  • logic_check.py 的黑名单从 6 条扩展到覆盖 AGENTS.md 中的每个"常见错误"。
  • 在 CLAUDE.md 触发路由表中增加一行：新 SQL 产出且含 OVI/bundle/scope 相关逻辑 → 自动 invoke sql-auditor subagent，审查通过后才可 commit。

#模块五：模型路由

它解决什么物理问题

不同模型有不同的 capability/cost tradeoff。用 Opus 执行 git push 就像用显微镜看路——能力过剩但成本浪费。

行业框架

任务特征适合的模型原因
需要长链推理、新问题、设计决策Opus（最强推理）复杂推理是 Opus 唯一不可替代的能力。
结构化任务、已知模式、SQL 生成Sonnet（高性价比）SQL 语法是高频训练数据，Sonnet 够用。
格式转换、模板填充、简单执行Haiku（最快最便宜）不需要推理能力。
代码审查、数据检查Sonnet需要覆盖面而非深度。

判断规则（实用版）：如果你能提前写出这个任务的每一步（step 1 做什么, step 2 做什么…），那它就不需要 Opus。Opus 的价值在于"我不知道该怎么拆解这个问题"的场景。

Notion AI 团队的公开分享：他们的 model router 先用一个轻量分类器判断任务复杂度，然后路由到对应模型。他们的数据显示 ~70% 的请求用 Haiku/Sonnet 就能达到 Opus 90% 以上的质量。

你目前的位置

96% Opus 使用。仅 subagent 用了 Sonnet。

#模块六：知识管理与 Retrieval

它解决什么物理问题

LLM 的参数知识（training data）有截止日期、有覆盖盲区、且无法保证准确。对于你的业务领域（CBRG 口径、表结构、指标定义），模型的参数知识完全不可用——这些是公司内部知识。

Retrieval 系统（RAG）的作用是在运行时把正确的知识注入 context，替代模型的参数记忆。

#二、如何持续迭代协作认知

核心原则：Agent Engineering 不是"学一次就会"的技能。它更像是一个持续追踪的领域——因为底层模型每 3-6 个月会有一次 capability jump，每次 jump 都会改变"哪些任务该让模型做 vs 哪些该人做"的边界。

L2：工程实践prompt engineering、agent architectureAnthropic cookbook/docs、行业公司技术博客每月看一次
L3：工具/框架Devin/Cursor/Claude Code 的功能更新工具的 changelog、GitHub release notes每次更新时看
L4：自己的数据token 消耗、session 效率、错误模式你本地的 stats-cache.json、transcripts每周看一次

来源说明URL / 搜索词

怎么判断一个新模型对你有没有用？

当一个新模型发布时，问自己三个问题：

  1. 它在 code generation 和 instruction following 上比前代提升了多少？（这是数据分析师最依赖的两个维度。）
  2. 它的价格和速度相比同级别模型是什么位置？
  3. 它的 context window 是否有变化？（影响你的 session 管理策略。）

L3：工具更新——怎么跟踪

  • Devin CLI：devin --version + GitHub release notes。
  • Claude Code：claude --version + Anthropic changelog。
  • 当工具大版本更新时，看一下它的 "what's new"——特别关注 session 管理、模型选择、缓存策略方面的变化。

L4：自己的数据——最重要但最容易忽略

建立一个月度 review 习惯（就像你做的 business WoW 监控）：

  • 每周 5 分钟：跑 stats-cache.json 分析脚本，看 top token consumer 和 session 步数分布。
  • 每月 30 分钟：回顾当月的 session 列表，标注哪些 session "效率高"（少步骤完成了复杂任务）、哪些"效率低"（多步骤但产出不大），找出 pattern。
  • 每季度：review CLAUDE.md 和 skills——哪些规则从来没被触发过？哪些新的错误模式需要加防护？

迭代方法论：OODA 循环

Observe → Orient → Decide → Act → (回到 Observe)
看 token 数据 → 对照行业实践 → 决定改什么 → 改 CLAUDE.md/skills → 测试效果

每次迭代只改一个变量——这是你作为数据分析师应该很熟悉的实验设计原则。不要同时改 system prompt + 换模型 + 调 session 长度，否则你不知道是哪个变化带来了效果。

#三、模型选型——从零开始的学习路径

Step 0：理解"模型"是什么

一个 LLM 模型本质上是一组固定的参数权重（比如 Opus 4 大约有数千亿参数）。更多参数 = 更强的推理能力 = 更贵 = 更慢。

同一代技术栈
Haiku（轻量）→Sonnet（平衡） → Opus（旗舰）
经济舱：速度快 / 便宜头等舱：最强推理 / 最贵

Step 1：理解定价结构

所有 LLM API 都按 token 计费。Token ≈ 0.75 个英文单词 ≈ 0.5 个中文字。

定价分两个维度：

  • Input tokens（你发给模型的内容）：system prompt + 历史消息 + 当前问题。
  • Output tokens（模型回复的内容）：模型的回答。

当前 Anthropic 定价（每百万 tokens）

模型InputOutputCache ReadCache Write相对成本
Haiku 3.5$0.80$4$0.08$0.801x
Sonnet 4$3$15$0.375$3~3.75x
Opus 4$15$75$1.875$18.75~19x

关键洞察：Opus 的 output token 价格是 Sonnet 的 5 倍、Haiku 的 18.75 倍。但 Opus 的推理能力并不是 Sonnet 的 5 倍——在大多数结构化任务上，差距可能只有 5-15%。

Step 2：理解能力差异在哪里

Sonnet 和 Opus 实际上差在哪？根据 Anthropic 官方 benchmark 和 Chatbot Arena 数据：

能力维度Sonnet vs Opus对你的影响
代码生成Sonnet ≈ Opus 的 95%+SQL 生成、Python 脚本几乎无差异。
指令遵循Sonnet ≈ Opus 的 90%+按 skill 步骤执行的任务差异极小。
长链推理Sonnet ≈ Opus 的 80-85%需要 5+ 步逻辑推导的分析有差距。
创造性/开放性Sonnet < Opus新工具设计、方法论创新有差距。
上下文理解Sonnet ≈ Opus 的 90%+理解已有代码、读懂复杂文档差异小。

实际结论：你的大部分工作（SQL 生成、dashboard 刷新、代码执行、文件编辑）都在 Sonnet 的能力覆盖范围内。只有"设计一个新的分析框架"或"从零搭建一套系统"这类开放性任务才需要 Opus。

Step 3：建立你自己的判断标准

不要依赖 benchmark，要做你自己的 A/B 测试。

方法：对同一个典型任务，分别用 Sonnet 和 Opus 各做一次，比较结果质量。你只需要做 5-8 个典型任务的对比就能建立直觉。

做完测试后，建立你自己的路由表——就像你做的 CBRG trigger 路由一样，只不过这次路由的是模型而非 skill。

Step 5：持续校准

每次 Anthropic 发布新版模型时（通常每 3-6 个月），重新做 Step 3 的 A/B 测试。因为：

  • 新版 Sonnet 可能已经追上了旧版 Opus 的推理能力。
  • 价格可能调整。
  • 新能力可能改变路由策略。
